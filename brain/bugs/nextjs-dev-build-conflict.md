# Next.js Concurrent Dev Server & Build Conflict (`.next` directory lock)

## Описание проблемы

Когда в терминале запущен локальный сервер разработки (`npm run dev`), запуск команды `npm run build` приводит к поломке dev-сервера (падение с кодом ошибки, отказ в обслуживании запросов `ECONNREFUSED` или ошибки отсутствующих манифестов в `.next/`). Разработчику приходится вручную перезапускать `npm run dev`.

---

## Причина возникновения

Оба скрипта Next.js работают с одной и той же директорией вывода: **`.next/`**.

1. **Монопольное владение и кэш dev-сервера:**
   Во время работы `next dev` процесс держит файловые дескрипторы и сокеты для горячей перезагрузки (Fast Refresh / HMR), скомпилированных JS/CSS чанков и манифестов страниц.
2. **Агрессивная очистка при `next build`:**
   Команда `next build` начинает свою работу с **полного удаления и очистки** каталога `.next/`.
3. **Блокировки файлов в Windows:**
   В операционной системе Windows процессы блокируют открытые файлы. Попытка `next build` перезаписать или удалить занятые файлы вызывает ошибку `EBUSY / EPERM`.
4. **Несовместимость артефактов:**
   Даже если сборка успевает записать файлы, `next dev` натыкается на production-структуру бандлов вместо dev-манифестов, в результате чего локальный сервер падает или перестает отдавать страницы.

---

## Правила и рекомендации

1. **Запрет одновременного запуска:**
   Никогда не запускать `npm run build` в фоне, если в активной сессии работает `npm run dev`.
2. **Проверка типов без сборки бандла:**
   Для валидации TypeScript кода без затрагивания директории `.next/` использовать:
   ```bash
   npx tsc --noEmit
   ```
   Эта команда компилирует только типы в оперативной памяти и не мешает запущенному локальному dev-серверу.
3. **Если требуется собрать продакшн:**
   Остановить `npm run dev` (`Ctrl+C`), выполнить `npm run build`, проверить результат, после чего при необходимости снова запустить `npm run dev`.
